# 像聊天软件一样用：方向、现状与分轮计划

开始日期：2026-11-11。本文记录这一阶段的目标、当天的盘点结论、每一轮做了什么以及还差什么。接口细节在各自的约定文档里，这里只留结论和指路。

## 目标

用起来像 Grok Bot：有名字的猫猫是联系人，选一只或一个群，说话、发资料、收结果。像聊天软件，不像工作区；开箱即用，日常使用不需要知道 Agent、模型、会话、上下文是什么。

两条不变的边界（完整纪律见 [AGENTS.md](../AGENTS.md)）：

- **底层复用 Clowder AI**。新能力先找固定版本、未打补丁的上游接口和事件，在适配层做组合、默认值和展示；不新增运行时补丁，不在 Bot 里另起一套执行、记忆或调度。
- **简单但不说假话**。失败、部分结果、等待确认都如实显示；「已受理」不等于「已完成」。

参照物的做法（来自 2026-11-11 读到的 Grok Bot 官方文档）：首次启动就有一个 bot 并直接进入对话；新建只要名字和头像，没有模型选项；群聊在「收件人」里选 2–6 个，群名自动生成；工作中可以继续发消息改方向，有「立即停止」；⌘K 搜联系人、群、消息和设置；资料页是「详情（定时）/ 资料库（文件）」；记忆和定时都靠在对话里说。

## 2026-11-11 盘点

对现有前端、适配层和上游能力各做了一次只读盘点，并在隔离运行时上实际建猫、聊天。最要紧的差距：

1. **回复不「活」**。发出消息后没有正在输入的样子，回复按草稿落盘的节奏整段出现，每次整页重绘，所有消息的入场动画重放；每次发送都闪一下「已排队」。引擎其实一直在推送逐字增量，前端没有用。
2. **首次启动走不下去**。没有猫时主区只有「选一个对话 / 左边是你的 Bot」；新建猫猫先看到 Agent、模型、推理强度、猫种。
3. **聊天里不能停**。停止要进抽屉 → 任务 → 调用卡片 → 点两次。
4. **等你确认的事要去运行面板**。聊天里只有一行提示。
5. **资料抽屉照着引擎的对象模型排**：轨迹（其实是合成回执）、上下文（永远为空）、执行 Agent、模型。
6. **缺少聊天软件的基本件**：搜索、按最近活动排序、时间、每个对话各自的草稿、新对话入口、加载更早的消息、群聊改名和成员管理、通知。
7. **措辞混杂**：Bot／猫猫、群组／分组，以及「原生成员配置」「Clowder AI 正在执行」之类的引擎用语。

## 部署到现有实例

日常实例直接从这个工作区运行：Bot 进程启动时加载 `server/`，页面从 `dist/client` 提供。所以升级就是「停两个服务 → （需要时）迁移数据、重建运行时 → `npm run build` → 启动」。新前端依赖新的适配层接口，前端和 Bot 进程必须一起换；只构建不重启会让新页面对着旧服务。

这一阶段第一次升级要多做两件事，都演练过：

1. 停止 Bot 和原生运行时（原生要等它正常退出，数据才写完整）。
2. `npm run data:move -- --apply --backup <备份目录>`：数据移到 `~/.clowder-bot`，原位置留链接（见 [维护说明](upstream-maintenance.md)「数据位置」）。启动方式里写死过数据路径的，改到新位置。
3. `npm run runtime:prepare`（数据目录指向新位置）：按新布局重建运行时，约五分钟（见「偏好仓库」）。
4. `npm run build`，再启动原生运行时和 Bot。
5. 核对：猫猫数量、各对话消息数与升级前一致；`/xbot-api/start` 能回答；`/xbot-api/memory/taste` 为 `ready`。

之后的升级只需要 `npm run build` 加重启 Bot，几秒钟。

## 实测中发现、暂时绕不过去的事

这些是引擎或部署前提的问题，适配层不能替它决定，先如实呈现并登记：

- **「记住这个偏好」**（已解决，待现有实例重建后生效）。原生只在「与构建同一个 Git 仓库里检出了 `main` 的工作树」里存偏好，没有配置项；以前的构建是独立的 detached HEAD，所以同意提议必然失败。现在 `runtime:prepare` 把构建建成数据目录里一个长期仓库的链接工作树，偏好落在数据目录，重建不丢；隔离运行时上已验证保存、读取和强制重建后的保留。细节与边界（公开偏好仍需使用者决定是否配置 `origin`）见 [维护说明](upstream-maintenance.md)「偏好仓库」。上游需求照旧登记：私有偏好应放在数据目录或提供受支持的定位方式。
- **猫读到了这个仓库自己的协作说明**（已有办法，新安装默认不再发生；现有实例待迁移）。猫的工作目录在 `<数据目录>/workspace/cats/<猫>`，而默认数据目录在本仓库里。Claude Code 会加载工作目录各级上层的 `CLAUDE.md`，Codex 会读 Git 根目录起的 `AGENTS.md`，所以每只猫每一轮都带着「前端必须委托…」「上游优先…」这些写给开发者的规则，以及这个仓库的 Claude 记忆索引；使用者个人的 Claude Code 钩子输出（提醒提交文档之类）也进了猫的会话。结果是回答被无关规则干扰，每轮的上下文更大、更慢、更贵（实测一条短回复带了约 3.9 万输入 token）。这不是引擎的问题，是部署位置的问题：运行数据应当放在任何代码仓库之外。现状：新安装默认把数据放在 `~/.clowder-bot`；现有实例用 `npm run data:move` 迁移（带备份，原位置留链接兼容旧路径）。隔离运行时上已演练：旧对话照常可用，新建的猫不再带仓库说明，首轮输入从约 3.9 万 token 降到约 2.9 万。见 [维护说明](upstream-maintenance.md)「数据位置」。个人级的 Claude Code 设置（`~/.claude` 里的技能、插件、钩子）按「沿用本机 Agent 的配置」的原则照旧生效，不由 Bot 改动。
- **「每天 9 点提醒我」现在走引擎的定时（新建或重新绑定的猫）**。原因（2026-11-11 调查）：引擎的定时工具（`cat_cafe_register_scheduled_task` 等，在 collab 这个 MCP 服务里）对猫可用，但只以「延迟加载的工具名」出现；Claude Code 二进制内置的 `schedule` 技能（云端定时）的触发描述更匹配「提醒我…」，于是被选中，结果既没有确认，也不出现在猫的定时列表里。做法：不改引擎，用上游受支持的成员级 `cliConfigArgs` 关掉 CLI 自己的定时技能与工具（`server/native/agents.ts` 的 `memberCliArgs`；见 `docs/xbot-api.md`「开箱即用」）。隔离运行时实测：Claude 猫（haiku）说「每天早上 9 点提醒我喝水」→ 调用 `cat_cafe_list_schedule_templates`、`cat_cafe_register_scheduled_task` → 「等你确认的事」里出现「想设一个定时 · 每天 09:00」→ 同意后出现在该猫的定时列表；Codex 猫不需要任何参数，同样走通。边界：只对此后新建或换过 Agent 的猫生效，已有的猫保持原样（不替用户改成员配置；在高级设置里重新选一次 Agent 即可）；上游自带的 `schedule-tasks` 技能仍未安装（要靠上游的技能同步），所以猫靠工具说明自己选对工具，不是硬保证；collab 服务自带的定时说明被历史补丁 P004 的进程内代理丢掉，记为该补丁的问题，不在其上扩展。留给上游的需求：部署级的 CLI 技能与工具开关、让定时工具默认可见、适合聊天部署的技能安装方式。
- **引擎自带的消息检索用不上**。证据索引是空的（没有配置嵌入模型），所以搜索由适配层当场读取各会话最新一页消息完成，范围是每个会话最近 200 条。
- **群里说话的规矩是引擎的**（实测）：不带 @ 的消息由一只猫接待；正文里写 `@名字` 就由那只猫回答；引擎的 `@all`／`@全体` 指这位用户的**所有**猫，不只是群成员，群外的猫会被成员检查拒绝（聊天里合并成一句「××不在这个群里，没有回答」）；猫在回复末尾顺口 @ 别的猫不会触发交接，行首的 @ 才会。所以群聊输入框里的「全体」插入的是每个成员各自的 `@名字`，不发 `@all`；路由本身不动。
- **八个模板里，目前只有三个的工具接得上**（2026-11-12）。引擎的本机工具检测列出 Codex、Claude Code、Kimi、DSH、AGY（Gemini）等；适配层能绑定的是前三种（`supportsRuntime`：不需要另外合成启动参数或插件配置的那几种），OpenCode 和 Antigravity 不在检测列表里。所以暹罗猫、小鲸鱼、狸花猫、孟加拉猫、金渐层这五只按模板建不了，新建猫猫时如实说明「这个应用还接不上 ××」，可以自定义借长相。接通更多工具需要逐个在真实环境里验证，登记为后续。
- **回复和它接住的追问分在两页上时不归位**（2026-11-12）。`follows` 按当前读到的一页计算；历史一页 200 条，回复在上一页末尾、追问在下一页开头时，回复留在原处。少见，先登记。
- **说话简短对正在进行的对话不立即生效；引擎一次只应用一个包**（2026-11-12）。引擎在会话开始、上下文压缩之后等时机才把身份（连同包里的默认行为）交给猫，平常接着聊的一轮不带，所以升级后老对话不会立刻变，开新对话最直接；固定的这版引擎只应用目录列表里的第一个包，引擎里已有别的包时适配层不装自己的，这条默认行为让位。包的安装在引擎里不是原子的，已登记为需要上游解决的事（[维护说明](upstream-maintenance.md)「引擎的包」）。
- **消息上的表情回应，引擎没有**（2026-11-13，登记为上游需求）。固定版本里，普通对话的消息没有回应字段，没有读写接口，猫的上下文里读不到，也没有给猫用的工具；只有多人频道（F290，进行中）有一套只记人的回应，服务端在仓库之外。现在的做法见第 16 轮：一个回应就是一条只有一个表情、引用那句话的普通消息，所以**发出后不能取消或更换，每一个都会叫醒猫回一轮**，猫也只能用「整条回复只有一个表情」来回应，做不到边干活边回一个 🛠、做完回一个 ✅。要去掉这些限制，需要上游提供四样：消息上的回应记录（一人一个、可取消，可沿用 `collective-reaction` 的五个表情与「回应不等于批准」的定位）；读写接口与事件；回应进入猫的上下文，并由引擎决定哪些回应叫醒猫；猫自己的「加回应」工具。上游有了以后升级固定版本接入，界面的 `reactions[]` 不用变，只换它的来源。
- **群里回复某只猫，靠适配层点名**（同日）。原生的路由只看 mentions，不看 `replyTo`；适配层在「引用的是一只猫的话、引擎的路由预览说这句话里没有点别人的名」时带上原生的显式 mentions。那只猫已经不在群里时不发送并说明原因。若上游让 `replyTo` 参与路由，这段组合可以撤掉。
- **只填名字建的猫没有归入原生的猫种**。未打补丁的建猫接口按新成员处理，头像和颜色来自所选猫脸；高级配置里「猫种」一项对这类猫没有意义。

- **「这台电脑」需要上游补的四件事**（2026-11-26，现在都由适配层在外面绕着做或如实说明，没有改引擎）。一、敏感能力的默认关闭：注册表安装一条 MCP 时对所有猫打开，按猫只有屏蔽名单，新建的猫只在「所有猫都屏蔽」时才继承屏蔽；适配层为此先装占位再指向驱动，并在建猫之前先把新猫的 id 写进屏蔽名单。希望有「默认关闭／允许名单」的登记方式。二、猫的身份：Claude Code 的 MCP 子进程环境里有 `CAT_CAFE_CAT_ID`，Codex 的没有，驱动因此分不清是哪只猫在操作（每只猫一个光标、按猫的记录都做不了）。三、撤权：一轮执行开始时拿到的工具带到这一轮结束，关闭开关只能靠取消整轮来立刻生效。四、审批：Claude Code 的猫以 `bypassPermissions` 运行，桌面操作不经过 Approval Hub，所以现在的许可只有「这只猫能不能用电脑」一档，做不到按应用或按动作询问。
- **几只猫同时用这台电脑，上游还没有能复用的协调**（2026-11-27）。现在的情况：几只猫可以同时开着，它们共用一个驱动和同一个桌面，动作由驱动排队逐个执行，猫和猫之间不知道对方在用哪个应用。对照过别家：云端产品给每个 Bot 一块自己的屏幕（Grok Bot）或一台自己的电脑（Dots）；同样用 cua-driver 的 OpenBot 没有协调；DS Bot 在自己的进程里做了应用租约（一个应用同一时间只给一个 Bot，到这一轮结束或空闲 60 秒放开）、前台租约和「使用者正在用键盘鼠标时先不动前台」。我们的调用不经过 Bot（猫的命令行直接连驱动），在 Bot 里加一层去拦等于重做运行时机制，所以看的是上游。上游的 F126「四肢控制面」目标一致，但读过固定提交 `fe632f8f` 的源码后结论是现在不能复用（只读了源码，没有运行）：租约在一次调用开始时拿、返回时就放（`LimbRegistry.invoke` 的 `finally`），续租、按猫释放、过期清理三个方法没有调用方；被占用时是拒绝，没有排队；租约对象是「设备＋能力」，分不到应用；按猫的策略（`LimbAccessPolicy.setPolicy`）没有调用方也没有接口，`gated` 一级直接拒绝、后面没有审批；设备调用的结果只以一段文本交给模型，截图到不了模型；桌面要挂上去还得另写一个插件或本机节点，把驱动的工具逐个翻成设备命令。希望上游补的五件：一、租约能跨多次调用持有到这一轮结束，结束或取消时释放；二、被占用时可以排队；三、比「能力」更细的租约对象（如应用）；四、按猫的策略可以配置，`gated` 接到 Approval Hub；五、设备调用的结果能带图片，或者允许设备直接以 MCP 服务接入。前四件是 F126 文档里写了、代码里还没有的。在那之前，适配层只在开关上做一条规则：同一时间只有一只猫开着，给一只猫打开时先把另一只关掉并结束它正在写的回复（见 [接口范围](xbot-api.md)「这台电脑」）。
