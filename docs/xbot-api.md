# XBot 兼容层范围

UI 保留 Bot 名称和文件夹概念，实际成员、执行和历史以 Clowder AI ID 为准。

| XBot 行为 | 原生映射 |
| --- | --- |
| Bot 创建/职责/重命名/删除 | `/api/cats`；删除成员保留原生历史 |
| 首次启动与只填名字建猫 | `GET /start` 把原生 Agent 检测说成「能不能直接开聊」；`POST /bots` 的 `simple` 用原生默认值建猫，见下文「开箱即用」 |
| 本地 Agent 接入 | `/agents` 原生发现；`/bots/:name/agent` 绑定执行者并恢复原生默认继承 |
| 单聊/新会话 | 原生 Thread，preferredCats 为该成员；新建保留旧会话 |
| 首次单聊的问候 | `POST /xbot-api/bots/:name/greeting` 以 `expectedThreadId` 绑定已打开的单聊，向这只猫发起一次普通的原生聊天请求 |
| 群聊 | 原生 Thread，preferredCats 为显式成员；消息路由保持原生；不填名字时以成员名命名。`PATCH /groups/:id {name?, add?, remove?}` 改原生标题与 preferredCats：`add`／`remove` 是猫的名字，表达「加谁、移出谁」，由适配层读出原生当前的成员后套用（已在群里的不重复加，不在的移出不算错），同一个群的修改在 Bot 进程内逐个执行，所以页面上的名单过期也不会把别处刚做的修改抹掉；结果少于 2 只或多于 10 只时 400。仍接受整份名单 `members`（与 `add`／`remove` 不能同时用），它按字面覆盖，只适合确知名单是最新的调用方。要移出的猫在群里还有进行中或排队的事时 409，不替用户停止。原生没有带版本条件的成员修改，另一个不经过 Bot 的写入方（例如运行面板）与之并发时仍以后写为准 |
| 找聊过的话 | `GET /search?q=` 当场读取每个会话最新一页原生消息并按聊天里的可见口径过滤，见下文「搜索」 |
| 发消息/回复引用 | `/api/messages`，原生 ID 与幂等键 |
| 历史/导出 | 原生消息；主界面最近 200 条，导出完整分页。单聊 `transcript` 与群聊 `GET /groups/:id` 都返回 `hasMore` 和上一页的游标 `before`，带 `?before=` 读更早的一页 |
| 新对话 | `POST /bots/:name/new`：原生新建一个 Thread，旧对话留在历史对话里；可带 `{expectedThreadId}`（页面正在显示的对话），与当前对话不一致时 409，不新建 |
| 状态/停止 | 原生 queue、activeInvocations、withdraw、cancel；单成员取消不取消兄弟任务 |
| 笔记 | 原生 `/api/memory` 会话 KV；旧 shared/bot scope 明确拒绝 |
| 上下文压缩 | 原生 compact-native；工具不支持时保留原生错误 |
| 定时任务 | 每猫 `/bots/:name/routines` 映射原生 reminder 模板及 schedule/tasks；创建、启停、删除、触发记录见 [接口说明](schedules-api.md) |
| 头像/文件夹/置顶 | Bot presentation store |
| 每只猫的强调色 | `bots[].accent {primary, secondary}` 取自原生成员的 `color`（只在两个值都是 `#rrggbb` 时下发），供聊天里做低调的强调色 |

运行面板补充原生队列、会话链、原生消息分页、记忆 catalog/search、Agent 与审批。F306 question/approval/elicitation 使用原生 revision、cardRef、operationId；其他支持内联操作的审批按原生 manifest 转发。需要完整原生会话卡片的交互不会自动批准。

## 开箱即用

`GET /xbot-api/start[?refresh=1]` 是原生 `/api/cats/native-runtimes` 检测结果的一句话版本，只读，不安装、不登录、不调用模型：

- `ready`、`agent {id, label, confirmed}`：新猫默认会用的本机 Agent。规则与旧的隐式选择相同：先取有登录记录（`configured`）的，其次是已安装且适配层能绑定的；`confirmed: false` 表示装了但没能确认登录。
- `blocked`：`null`、`login_required`（有装好但需要登录的）或 `no_agent`。
- `agents[]`：适配层能绑定的那几种（Codex、Claude Code、Kimi）各自的 `state`：`ready`、`unknown`、`login`、`missing`，以及原生给出的 `loginCommand`。
- `cats`：现有猫的数量。
- `faces[]`：可以选的猫脸，各带它在引擎里的同名模板的画像和它用的 Agent：`{id, rev, name?, nickname?, role?, personality?, strengths?, tool}`。
  - 画像来自未打补丁的上游 `GET /api/cat-templates` 的 `roleDescription`／`personality`／`teamStrengths`，各压成一行并截断；`rev` 随画像内容变化，建猫时带回（见下）。`name` 是上游模板的叫法（布偶猫、小鲸鱼…），`nickname` 是模板给这只猫起的名字（宪宪、鲸鲸…），可以作为建议的名字。挑哪张脸，建出来的猫就以这份画像起步，所以首屏和新建猫猫要把它的特点简短地说出来。
  - `tool {label, state, usable, id?, reason?, loginCommand?}`：**这只猫用哪个 Agent 思考是模板的一部分**（使用者 2026-11-12 指出：选了暹罗猫还能在下拉里挑 Codex 不合理；字段名 `tool` 照旧）。`usable` 为真时可以按这张脸原样建猫，`id` 是它会绑定的本机 Agent；否则 `reason` 用一句话说为什么（「这台电脑上还没有装 Kimi」「暂不支持 AGY Native」「Codex 还没有登录」），`state` 是 `ready`／`unknown`（装了，登录没能确认，可以试）／`login`／`missing`／`unsupported`。应用还不支持的 Agent 先说不支持：装上也不会变（2026-11-13 起这句话是「暂不支持 …」，原来是「这个应用还接不上 …」；使用者认为后者不像人说的话）。
  - 脸和 Agent 的对应来自固定上游 `cat-template.json` 的猫种配置（`breeds[].variants` 的默认项）：布偶猫 Claude、缅因猫 Codex、暹罗猫 Gemini（AGY）、梵花猫 Kimi、狸花猫与金渐层 OpenCode、孟加拉猫 Antigravity；小鲸鱼是 DSH 运行时的猫。上游的模板接口自己注明是「纯灵魂层，不含 client/model 绑定」，没有受支持的接口给出这层对应，所以放在适配层的 `faceTools`（`server/native/agents.ts`）里，由 `tests/face-tools.test.ts` 对着固定上游的文件核对。适配层目前能接的只有 Claude Code、Codex、Kimi 三种（`supportsRuntime`），所以在只装了前两种的电脑上，能按模板建的是布偶猫和缅因猫，其余的脸只能「自定义」借长相。
  - 顺序是引擎模板的顺序（也是客户端头像库的顺序）；引擎没有对应模板的脸不在其中，模板缺颜色（建猫会被拒绝）的也不在其中；模板读不到时是空数组，首屏其余内容照常。引擎用 ACP 跑的成员在 Agent 检测里以 `acp:<成员>` 出现，按它的 client 归到对应的脸上（只影响怎么称呼这个 Agent，这类接入应用仍不支持）。

`POST /xbot-api/bots` 增加第三种请求体 `{name, simple: {face?, rev?, custom?, about?, personality?, agent?}, idempotencyKey}`：

- 只调用**未打补丁的上游** `POST /api/cats`（固定版本 `42017e0` 的 `routes/cats.ts`），与历史上的 fork／导入路径是同一个原生接口；不经过本地补丁 P005 的 `/api/bot-cat-templates/instantiate`。带 `catConfig` 的完整创建仍走 P005，那是待退出的历史补丁，不因这个流程而扩展。
- 请求体只有成员本身的字段：`catId`、名字与别名、所选猫脸对应角色模板的颜色、职责／性格／简介、`clientId`、`configurationSource: 'native_tool'`、`defaultModel: ''`。模型与推理强度不写，沿用该 Agent 的本机默认。不传 `breedId`，由原生按新成员处理；头像只存在 Bot 的展示数据里。
- `face` 是八张猫脸之一，决定头像和颜色，**也决定这只猫是谁、用哪个 Agent**：默认按模板建，职责、性格、擅长取引擎里同名模板的原文（与 `faces[]` 里给界面看的是同一份），Agent 是这张脸自己的（`faces[].tool`），不另选。模板里没写的项用通用的「随叫随到的伙伴」补上。
  - 这张脸的 Agent 在这台电脑上用不了时，创建在询问原生之前被拒绝：422，`code: 'face_unavailable'`，原因就是 `tool.reason`，并说明怎么办（没装的：装好再试或改用自定义；暂不支持的：改用自定义；没登录的：登录后再试）。
  - 按模板建时 `simple.agent` 可以不带；带了而且不是这张脸的 Agent，422，`code: 'face_tool'`（「这只猫猫用 Claude Code 来思考，不能另选；想自己选，请用「自定义」」）。
  - 不带 `face`：取 `simple.agent`（没有就取上面的默认 Agent）对应的那只猫——Claude Code 是布偶猫，Codex 是缅因猫，Kimi 是梵花猫。
- **说话简短（默认，没有开关）**（使用者 2026-11-12：猫的回复不要太啰嗦，这是聊天软件与工作区式 Agent 的区别之一；同日又说：「说话简短作为一个默认选项，不需要按钮配置」）。每只猫都被叮嘱一句聊天时怎么说话（`chatManner`，`server/native/chat-pack.ts`）：「说话像在聊天软件里回消息：先说结论，通常两三句话说完；不用标题、列表、表格和表情符号，不复述问题，不铺垫，不在结尾总结。对方明确要清单、表格、代码或长文时照给；内容确实多时先说要点，问一句要不要展开。对方只是道谢、道别，或只回了一个表情，而你没有别的要说、也没有要接着做的事时，只回一个表情就够了，不必写字。」（最后一句是 2026-11-13 加的：只有一个表情的回复会画成你那句话上的回应，见[聊天体验适配契约](chat-experience-api.md)「回复与表情回应」。）它不写进任何一只猫的资料，而是引擎的一个 Pack（上游 F129，未打补丁的 `GET /api/packs` 与 `POST /api/packs/add`）：适配层让引擎里一直装着一个只含这一条默认行为的 style 包 `clowder-bot-chat`（`defaults.yaml`：`scope: all-cats`、`overridable: true`），引擎把它编进每只猫身份提示里的「默认行为（用户可覆盖）」一节。所以在这里建的、以前建的、按模板的、自定义的、用哪个 Agent 思考的猫都一样，不需要逐只设置。
  - 什么时候装：给猫发消息、请猫打招呼之前，先确认引擎里有这个包（确认过的十分钟内不再问，按只进不退的时钟算）；Bot 启动时也装一次，引擎自己叫醒猫（到点的提醒）时它已经在。引擎里没有、或版本不同就安装：两份文件写进一个临时目录，交给引擎复制进它自己的包目录（`<数据目录>/native/workspace/.cat-cafe/packs/clowder-bot-chat`，随数据保留、重建运行时不丢），临时目录随即删掉。版本号带着这句话的摘要，措辞一改，装着的包就被替换。消息最多为它等 2.5 秒，引擎慢的时候消息先走、安装自己接着做完；装不上不拦消息：猫照常回答，只是啰嗦一些，下一条消息再试，日志里只说一次。一次安装请求没有好好回来之前，不因为引擎列出了这个名字就当它装好了（引擎替换包是先删后拷，列表只看清单文件），会重装一遍。
  - 没有开关：`GET /xbot-api/bots/:name` 不再有 `concise`，`PATCH /xbot-api/bots/:name` 不认这个字段（400）。建猫不再往性格里加任何话，猫的 `personality` 就是模板或使用者写的原话。想让某只猫这一次多说一点，在对话里直接告诉它：这是一条可以被使用者的话盖过的默认行为，不是硬约束。
  - 实测（隔离运行时，2026-11-12，同样两个问题，各在新对话里）：Claude haiku 猫不带它 387 字 32 行、600 字 35 行（标题、列表、表格、表情）；带它 124 字 3 行、166 字 3 行，明确要表格时照样给表格。Codex 猫同一个问题 137 字 3 行。
  - 边界：引擎在把身份交给猫的时候带上它——一段会话开始时、上下文被压缩之后、成员名单变了之后、会话恢复重来时；平常接着聊的一轮不重新带。所以升级后正在进行的对话不会立刻变简短，开一个新对话是最直接的办法。固定的这版引擎一次只应用一个包，即它目录列表里的第一个（不是安装的先后，F129 Phase A）：引擎里已经有别的包时，那是使用者自己的，适配层什么都不装也不动它（装了可能排到前面把它顶掉），这条默认行为不生效，日志里写明；那个包移走之后，下一条消息时自动装上。
- 自定义（不按模板）：带 `custom: true`，或者写了自己的话（`about` 一句用途，成为职责与简介；`personality` 性格，≤500 字）。这时猫脸只是外观，任何一张脸都可以配这台电脑上能用的 Agent：`simple.agent` 指定，不带就用默认的那个；没写的项用通用的「随叫随到的伙伴」和「亲切耐心，讲得清楚」。2026-11-12 之前只填名字建的猫都是这份通用画像，不受这次改动影响。
- 建出来的就是看到的那只：按模板建时带上 `faces[]` 里这张脸的 `rev`。引擎里这份画像在页面读取之后变了，创建会在询问原生之前被拒绝（409，`code: 'face_changed'`），页面应重新读取 `/start`、让用户再看一眼。不带 `rev` 时按当前模板建。自定义不受它影响。
- 模板读不到（或这张脸没有可用的模板和颜色）时创建被拒绝：503，`code: 'faces_unavailable'`，「暂时读不到猫猫的资料，这次没有创建」。这时还没有向原生发出任何创建请求，所以不是「结果不明」；自定义也需要模板里的颜色，同样建不了。
- 重发（应答丢了，同一个键、同样的内容再来一次）按已知的事实回答：
  - 本进程里记得这次请求：把第一次解析出来的原生请求原样重放（Agent、模板当时的原文都不重新解析），所以即使模板在两次之间变了，原生看到的仍是同一个请求。这份对应关系只留在进程内存里（最近 50 个），不写入展示数据。
  - 上一次什么都没建出来、而当时解析到的 Agent 现在用不了了：按现在的情况重新解析，不会在一个已经不在的 Agent 上建猫。
  - 进程重启过、不记得这次请求，但这个键建出的那只猫已经在（`catId` 由键推导）：直接回答这只猫，不再向原生发创建，也不按现在的模板和 Agent 重新解析——不会对一只已经建好的猫说「没有创建」或「介绍变了」。能从猫身上核对的（名字、脸、Agent、自定义时写的话）与请求不符时，按「不是同一个请求」拒绝（409）。
  - 同一个键换了内容，而原来那次已经建出了猫：409，不再询问原生。同样的请求同时到达两次，只解析一次，两次到达原生的是同一份内容。
- 上游的模板接口不校验条目，适配层读取时只保留格式正确的字段：不是对象、没有 `id` 的条目跳过，类型不对的字段当作没写。
- 上游有几个模板的职责本来就写着它用的模型或 Agent（狸花猫「GLM 对话猫」、孟加拉猫「混血多模型 agent…」、金渐层「开源多模型编码 agent…」）。现在按模板建的猫用的就是模板自己的 Agent，这些话与事实一致；它们的 Agent 这个应用还不支持，所以这几张脸目前只能自定义。模型本身不写进成员（`defaultModel: ''`），沿用那个 Agent 在本机的默认配置。
- 幂等用上游成员创建自带的请求身份：请求头 `x-cat-cafe-onboarding-journey: clowder-bot-simple` 与 `idempotency-key: onboarding:clowder-bot-simple:cat:<idempotencyKey>`（`config/member-create-receipt.ts`）。`catId` 由 `idempotencyKey` 推导，所以同一个键、同样的内容重发得到同一只猫；同一个键换了内容由原生拒绝（409）。重发时如果那只猫已经在，就不再按当前的 Agent 检测结果拦截。这一路径 2026-11-11 在隔离运行时上实测过创建、重放和冲突。
- 绑定 Claude Code 的猫，成员记录里带一组默认的「额外 CLI 参数」（上游成员编辑里的 `cliConfigArgs`，受支持的成员级设置）：`--settings {"skillOverrides":{"schedule":"off","loop":"off"}} --disallowedTools RemoteTrigger,CronCreate,CronDelete,CronList`，关掉 CLI 自带的云端定时，让「每天 9 点提醒我」走引擎的定时工具和它的确认。Codex 没有自带定时，不写参数。它是成员建好之后单独的一步（`PATCH /api/cats/:id {expectedRevision, cliConfigArgs}`），三种创建方式都一样；创建请求本身不带这组参数，形状始终是原生按幂等键记下的那个，所以默认值以后怎么变，重发旧请求都不会被当成「内容不同」。成员已有参数时不动（包括用户后来自己改的）；写入被拒绝时按成员当前的版本再试一次，仍不成功则猫照常建好，应答多带一句 `notice` 说明少了什么、去哪里补，不把它说成完全建好。`PUT /bots/:name/agent` 换 Agent 时在同一次修改里写入。设置 JSON 里不能有空白：上游按空白切分参数。只影响此后新建或重新绑定的猫，已有的猫不改。
- 必须带 `idempotencyKey`；不能与 `catConfig`、`runtimeId`、`templateId`、`persona`、`description` 混用。没有可用的 Agent 时 422，说明要先装好并登录。两种 409 用 `code` 区分：同名是 `name_taken`（改名、其他创建方式的同名也带这个码），同一个键换了内容是 `request_changed`。

`POST /xbot-api/groups` 带 `members` 时 `name` 可省略，群名取成员名用「、」连接（超过 64 字截断），之后可改名。可带 `idempotencyKey`（UUID）：它同时是群目录的名字和原生 Thread 创建的幂等键，应答丢失后用同一个键重发得到同一个群，不会建出第二个：这个键已经建过群时，适配层直接返回那个群现在的样子（200），不再把创建请求发给原生——原生对重复的键会返回同一个 Thread，但会把请求里的成员再写一遍（固定上游 `routes/threads.ts`），那样会把之后改过的成员改回去，也绕过了改成员时「还在忙的不能移出」的检查。群名是原生 Thread 标题，按自由文本校验；不带 `members` 时同一路由仍是建侧栏分组，分组名沿用原来的字符限制。

## 搜索

`GET /xbot-api/search?q=<1–100 字>` 返回 `{query, results[], more, searched, failed}`。每条结果是 `{chat:{type:'bot'|'group', id, name}, threadId, current, messageId, time, from:'owner'|'cat', catName?, snippet, match:[起,止]}`，按时间从新到旧，最多 30 条。

- 范围是用户自己的会话：每只猫当前的对话和它的历史对话（`current:false`，需要先从历史对话里打开）、所有群聊；各取最新一页（200 条）原生消息，搜索时当场读取，不建索引、不留副本。
- 可见口径与聊天一致：用户消息（应用代发的开场邀请除外）和可见的猫回复；草稿、处理中、`SILENT`、被显式发言取代的执行记录不算，匹配的是去掉署名后的显示文字，不区分大小写。
- 猫的回复按显示出来的文字匹配和摘录：标题、列表、引用、表格、粗体、行内代码、链接地址这些 Markdown 记号不出现在 `snippet` 里（`server/native/text.ts` 的 `plainLine`），`match` 指向去掉记号后的位置；只在带记号的原文里才匹配得上的词（例如搜 `` `npm ci` ``）按原文摘录。用户自己打的字不改。会话列表的预览行 `activity.last.text` 用同一规则。
- `GET /xbot-api/bots/:name/search?q=` 与 `GET /xbot-api/groups/:id/search?q=` 是同一个搜索，只看这一个聊天当前的对话，返回形状相同；用于「在这个聊天里找」，不会被别的聊天的结果挤掉。
- `more` 表示还有没返回的匹配，或有会话存在更早、这次没看的消息；`failed` 是没能读取的会话数，前端要如实说明，不当作「没有结果」。
- 固定上游自带的消息检索（`/api/evidence/search?resultUnit=message`）依赖证据索引，2026-11-11 在隔离运行时和现有实例上实测都返回空（`passages_count: 0`，未配置嵌入模型），所以这里没有用它；索引可用后可以改为调用原生检索，接口形状不变。

问候复用固定版本 `42017e0c` 的 `POST /api/messages`。原生身份上下文包含猫名、角色说明与性格（`assets/prompt-templates/s1-identity.md`）。适配层指定单个成员、`next_work` 与同一猫和会话的稳定幂等键。首次请求先检查原生历史和队列，已有对话返回 `exists`。检查与准入是两个操作，并发到达的用户消息由原生队列决定顺序。创建猫和读取历史各自独立，生成失败时猫仍可正常聊天。

开场时，人设只影响问候的语气。普通昵称、意象和含义不明的名字以问好收尾。只有名字本身直接表达了一件要做的事，猫才顺着问一句，让用户自己说明想从哪里开始。

接口收到原生邀请记录的 ID 后返回 `accepted`。猫的实际回复和执行失败从历史及活动接口读取。等待回执时，Bot 记录邀请措辞的版本，保证升级后的重试仍用原键和原文。收到回执后只保留原生消息 ID，聊天页据此收起应用代发的邀请。原生历史与导出保留原文。若传输中断而未确认回执，`transcript.greeting.status` 为 `unconfirmed`，由用户显式重试。

`transcript` 为兼容 XBot 渲染器生成的投影，包含原生消息对象和 `native_message_id`。显示用 `send_message_to_user` 行带 `presentation_receipt: true`，不可计入模型工具调用/成本。真实工具轨迹来自 `toolEvents`。Bot 不自行估算或编造 Token。

回复进行中的呈现见 [回复的实时呈现：接口约定](chat-live-api.md)：同一条 SSE 在原生事件之后追加精简的 `live` 事件（开始、思考、步骤、正文增量、结束），会话行用 `in_progress` 标出还在写的回复，不再用占位文字；紧跟在问题后面的回复不重复引用上一句。

单聊与群聊的显示正文省去回复末尾的猫爪署名。固定上游 `42017e0` 的 `extra.outputLayout.hostTail` 提供署名范围，适配器核对线程、成员、轮次与正文长度及 SHA-256 后裁掉该范围。有范围但验证失败时保留原文。没有范围的旧记录，只识别 Markdown 代码围栏之外、末尾独占一行的 `[名字/模型🐾]` 或 `[名字🐾]`。有的模型把署名写在回复开头（真实群聊里出现过「[快手/Haiku🐾]」独占第一行、正文在后面）：署名里的名字就是发言的这只猫、且后面还有正文时，开头这一段也不显示；别的猫的署名、不在开头的都保留。用户消息、原生 `native` 对象和历史导出保留原文，新回复与历史读取共用这个展示转换。

单聊与群聊消息包含 `presentation_kind: "message" | "activity"`、`native_cat_id` 和 `speaker`（真实发送成员的 ID、名称和头像元数据；成员不可用时为 null）。只有当前返回页存在同一成员、同一原生 turn 的显式 callback 发言，才将对应 stream 累计记录投影为 `activity`；它不再生成聊天发送回执。前端将其显示为默认折叠的执行过程，正式发言保持原生顺序与各自时间戳。关联依赖精确执行身份，不用文本、时间接近程度或跨成员共享的外层 invocation ID 推断。错误、取消和缺少关联证据的回复继续作为普通消息；跨分页的关联暂不推断。该投影不修改或删除原生历史。

未迁移的跨设备、云账号、语音、完整 skills 配置返回 supported=false 或明确 4xx/501。应用自 2026-11-26 起有第一版（微信、自定义应用），接口见 [应用：第一版接口](apps-api.md)；旧 XBot 的 `/xbot-api/apps` 应用商店格式不再沿用。定时任务首版提供单猫创建、查看、启停和删除，尚不提供编辑已有计划、手动立即触发和高级调度治理。资料导入里的旧 XBot routines 格式仍拒绝，以免绕过原生计划校验。未读数量目前尚未从原生 read cursor 完整映射，不应将列表零值用于业务统计。

旧 `/models`、`/providers`、`/providers/*`、`/setup/key`、`/bots/:name/binding` 已退役为 410。Bot 新建和更新不再接受模型配置；更换 Agent 走专用绑定接口，避免普通资料更新意外改变接入。原生管理 API 中的账号能力不随 XBot 旧逻辑删除。

## 这台电脑

一只猫可以看到并操作这台电脑上的应用（2026-11-26，第 18 轮）。没有云电脑：就是使用者自己的这台机器，所以界面上叫「这台电脑」。本轮只有 macOS。

**分层。**

- 上游原生、未改：能力注册表（`GET/PATCH /api/capabilities`、`POST /api/capabilities/mcp/install`、`DELETE /api/capabilities/mcp/:id`）——一条 MCP 登记，和它按猫的开关；一轮执行的工具调用事件；停止一轮。谁能用电脑只记在注册表里，适配层不另存一份。
- 外部驱动、不属于本仓库：[cua-driver](https://github.com/trycua/cua)（MIT）自带的已签名应用 `CuaDriver.app`。截屏和输入都在它自己的后台进程里做，macOS 的两项授权（辅助功能、屏幕录制）给的是它，所以与 Bot 怎么启动无关。这个后台进程由驱动的 MCP 入口按需自己拉起，Bot 不看管任何进程。版本固定在 `computer-driver.lock.json`，用 `npm run computer:install` 安装（见 [维护说明](upstream-maintenance.md)「电脑驱动」）。
- 适配层（`server/native/computer.ts`、`server/xbot/computer.ts`）：读状态、开关的组合步骤、新建猫后的补关、把用到这条登记的步骤标出来。

**接口。**

`GET /xbot-api/bots/:name/computer` →

```json
{ "supported": true, "installed": true, "on": false, "permissions": "granted" }
```

| 字段 | 含义 |
| --- | --- |
| `supported` | 这个系统上有没有可用的驱动。`false` 时界面不出现这一项 |
| `installed` | 机器上找到了签名正确的 `CuaDriver.app`。查找顺序：`BOT_COMPUTER_DRIVER_APP`（只接受绝对路径）、`<数据目录>/tools/CuaDriver.app`、`/Applications`、`~/Applications`；只认满足签名要求的那一份（bundle id `com.trycua.driver`、Developer ID 团队 `YCK386LBJ7`，用 `codesign --verify --deep --strict -R=…` 一次核对），用的是解析后的真实路径，登记进引擎的也是这同一个路径。核对结果按驱动程序文件的身份（设备、inode、大小、修改时间）缓存 60 秒，文件变了就重验；打开开关、要把登记指向它之前一定重新核对 |
| `on` | 这只猫现在能不能用：注册表里 `computer` 这条登记没有把它列在屏蔽名单里。每次现读 |
| `permissions` | 驱动自己的 macOS 授权：`granted`、`needed`（另带 `missing: ["accessibility" \| "screen_recording"]`）、`unknown`。`unknown` 是常态：驱动的后台进程没在运行时读不到，不是故障 |
| `others` | 给这只猫打开时要让出电脑的猫的名字，没有就不出现：别的开着的猫（正常情况下只有一个），以及开关已经关掉、但还有一轮没停下的猫（读的时候现看一眼，自己停下了的不列）。给这只猫打开时，前者被先关掉，两者正在进行的回复都会被结束，见下文「同一时间只有一只猫」。名字查不到时是空字符串 |

`PUT /xbot-api/bots/:name/computer {"enabled": true|false}` → 同样的结构，是改完之后的样子。

打开时依次做（任何一步不成立就停在那里，按下表如实回答）：

1. 找到驱动；读它的授权。后台进程没在运行就用 `open -n -g CuaDriver.app --args serve` 启动一次（经 LaunchServices，它才是自己的责任进程），缺授权时驱动自己会打开系统设置。
2. 授权不全：**什么都不改**，回答 `on: false, permissions: "needed"`。界面等使用者授权后把同一个请求再发一次。注册表在读到授权之前不写。
3. 注册表里还没有这条登记：先装一条什么都不提供的占位（`/usr/bin/true`），用原生的一次调用对所有猫屏蔽（`PATCH … {scope: "project", enabled: false}`），确认没有任何猫开着，再把它指到驱动（原生在覆盖安装时保留屏蔽名单），再确认一次。这样做是因为原生安装一条 MCP 时默认对所有猫打开，按猫的控制只是一份屏蔽名单；按这个顺序，登记过程中没有一刻是别的猫能用的。任何一步确认不了就把登记删掉。
4. 别的猫开着的话，先把它们关掉（见下文「同一时间只有一只猫」）；有一只确认不了已经关掉并停下，就到此为止，这只猫不打开。
5. 对这只猫解除屏蔽（`PATCH … {scope: "cat", catId, enabled: true}`），再读一次确认。这一步不管刚才读到的是开是关都会写：之前某次超时的请求可能还排在引擎里，原生按到达顺序应用，后写的为准。开没开成以读回来的为准：写入的应答丢了但读回来是开着，就是开成了；读不回来就是不知道，502 `computer_on_unknown`，不说「没能打开」。

关闭：把这只猫加回屏蔽名单并确认（同样总是写）；没有任何猫开着时请驱动的后台进程退出（`cua-driver stop`，尽力而为）。登记本身留着、对所有猫屏蔽：此时原生会让新建的猫自动继承屏蔽。关闭不依赖驱动是否还在。注册表里没有这条登记时（比如打开到一半、等系统授权时使用者点了「不等了」，界面此时发一次关闭），什么都没有开过：只请为那次打开而启动的驱动进程退出。

**关闭立刻生效。** 一轮执行开始时拿到的工具会一直带到这一轮结束，光写屏蔽名单管不到正在进行的那一轮。所以每次关闭（不看登记里读到的是开是关，也不管屏蔽那次写入成没成：上一次关闭可能写完屏蔽就失败了）都会用原生的取消把这只猫正在进行的各轮结束掉——它自己的对话和它所在的每个群，逐个 `POST /api/threads/:id/cancel/:catId`，同一对话里别的猫不受影响。那条回复会像被点了「停止」一样中断。取消只是请求：要等到该对话的队列里不再列出这只猫的调用才算结束，最多等 6 秒；原生回答没有取消、队列读不到、或到时仍在，都按「还没停下」如实回答。只有注册表里根本没有这条登记（从没有猫拿到过工具）时才不做这一步。隔离运行时上实测（一只猫正在连续操作计算器）：关闭 0.2 秒应答，那一轮的结束事件 1.1 秒后到达，之后没有再出现电脑步骤。

**同一时间只有一只猫。**（2026-11-27）几只猫共用一个驱动和同一个桌面，驱动只保证动作逐个执行，猫和猫之间不知道对方正用着哪个应用；上游目前没有可以复用的协调（F126 的租约只包住一次调用，见 [路线图](chat-app-roadmap.md)「实测中发现、暂时绕不过去的事」）。调用不经过适配层，适配层能守住的地方只有开关，所以规则放在这里：给一只猫打开时，先把其他开着的猫逐只关掉，做的事和关它自己的开关一样——写屏蔽、读回确认、用原生的取消结束它正在进行的各轮（那条回复像被点了「停止」一样中断）——全部确认之后才给这只猫打开。过程中没有一刻是两只猫都能用的；驱动的后台进程不停。

- 以注册表读回来的为准，不看写入的应答：应答丢了但写进去了，照常往下做。
- 有一只猫的屏蔽读回来仍是开着：不给这只猫打开，502 `computer_other_on`。已经关掉的那些猫，正在进行的各轮照样结束，句子里也说明它们的已经关掉了；仍开着的那只，回复不动。
- 屏蔽发出去了，但注册表读不回来：那些猫可能已经关掉，所以照样请求结束它们正在进行的各轮（不然下一次会读到它们已经关着，直接给这只猫打开，而那一轮没人结束过）；不给这只猫打开，502 `computer_other_on`，句子说的是「没能确认……已经关掉」，不说「没能关掉」。取消只是请求：这一回答不代表那些轮已经停下，没确认停下的下次打开时会再问。
- 屏蔽都确认了，但有一只猫正在进行的某一轮没能确认停下：不给这只猫打开，502 `computer_other_running`；那只猫的开关已经是关的。等它停下后再开一次即可。
- **被拿走电脑的猫，记到「确认关着、也确认停下」为止。** 一只猫在屏蔽**发出之前**就记下（适配层内存里的一份 id 名单，换猫和它自己的关闭都记），只有在「注册表刚读到它是关的」并且「看不到它还有正在进行的一轮」时才划掉，或者它自己被重新打开时划掉。名单上的猫只要读到是关的，之后给任何猫打开都会先对它再取消一次并再等，没停下就仍然不开（`computer_other_running`）：注册表里虽然没有猫开着，那一轮手里还有工具。这也管住了迟到的写入：屏蔽在这边超时、当时读回来仍是开着（回复不动，这只猫不打开），之后才在引擎里落地——下一次打开时它读到是关的、又在名单上，它的各轮会先被结束。读不回注册表时取消过也不划掉（它可能还开着、又开始了新的一轮）。这份名单只是请求簿记，谁开着仍只看注册表；它只在内存里，Bot 重启即丢（那一轮自己结束后就不再有影响）。
- 别的猫都关掉并停下之后，这只猫自己的开关没能写成（读回来不是开着）：此时没有猫开着，502 `computer_not_on`，句子里说明哪只猫的已经关掉了。读不回来：502 `computer_on_unknown`，句子说「没能确认这只猫的有没有打开」（它可能已经开着），同样说明哪只猫的已经关掉了。没有别的猫要关时，写入失败的回答和以前一样，读不回来同样是 `computer_on_unknown`。
- 换不过去的三种拒绝都没有给这只猫写任何东西：它原来关着就仍关着（句子说「所以这只猫的没有打开」），原来就开着（规则之前留下的状态，或同一个请求发了两次）就仍开着（句子说「这只猫的本来就开着」）。
- 句子里说猫的方式和确认框一致：名字各带「」并排写，查不到名字的说「另一只猫」，不止一只说「另外几只猫」。
- 缺系统授权时什么都不改，原来开着的猫照旧。
- 注册表里已经有两只以上开着的猫（这条规则之前留下的，或别的客户端写的）时，谁都不会被自动关掉；下一次给任何一只猫打开时，其余的一起关掉。新建猫、关闭、读状态都不受这条规则影响。

| 情况 | 回答 |
| --- | --- |
| 这个系统没有驱动 | 422 `computer_unsupported` |
| 没装驱动 | 422 `computer_absent` |
| 启动后 6 秒内驱动没有应答 | 503 `computer_not_started` |
| 登记过程确认不了，已撤回 | 502 `computer_not_registered` |
| 登记过程确认不了，而且没能撤回 | 502 `computer_half_registered`，提示到每只猫的资料里确认是关着的。留下的至多是占位（不提供任何工具），下次打开会重新来过 |
| 开或关之后读回来不是想要的状态 | 502 |
| 打开时没能先把另一只猫的关掉，或确认不了它已经关掉 | 502 `computer_other_on`，句子里带那只猫的名字；没有给这只猫写任何东西。确认不了时会请求结束那只猫正在进行的各轮，但不代表已经停下 |
| 打开时另一只猫已经关掉并停下，但这只猫自己的开关没能打开 | 502 `computer_not_on`，句子里带那只猫的名字：现在没有猫开着，再开一次即可 |
| 给这只猫的开关写过了，但注册表读不回来 | 502 `computer_on_unknown`：不知道开没开成，句子如实说；有别的猫被关掉时带它的名字 |
| 打开时另一只猫已经关掉，但没能确认它正在进行的某一轮已经停下 | 502 `computer_other_running`，句子里带那只猫的名字：请使用者到它的对话里点停止，然后再开一次。没有给这只猫写任何东西 |
| 已经关掉，但没能确认它正在进行的某一轮已经停下 | 502 `computer_still_running`：开关是关的，那一轮停下之前它还能用；请使用者在对话里点停止，或稍后再关一次（再关一次会再取消一次） |

两个开关请求不会交叉执行（进程内排队）；Bot 重启不丢状态，因为状态都在注册表里。

**删除一只开着的猫。** `DELETE /xbot-api/bots/:name` 对一只开着的猫（或在上面那份名单里的猫）先做一次和关它的开关一样的事——写屏蔽、读回、结束它正在进行的各轮——确认它关着并且停下之后才删除。原因：一轮执行带着开始时拿到的工具直到结束，原生删除一只猫并不结束它正在进行的一轮，而删除之后适配层连它的对话也不记得了，那一轮就再也找不到；之后给别的猫打开，就成了两只猫同时在用。做不到时不删除，409：`computer_still_running`（它用着电脑的那一轮还没停下：请使用者在它的对话里点停止，然后再删一次；此时它的开关已经是关的）或 `computer_still_on`（没能确认它已经用不了电脑，包括注册表读不到的时候）。没有用过电脑的猫照旧删除，不多写任何东西。删除和开关走同一个进程内队列：换猫进行到一半时到达的删除会等换猫做完。经 `/native-api` 或引擎自己的界面删猫不走这一步。

**新建的猫默认不能用电脑。** 原生的规则是：所有猫都关着时新猫继承屏蔽，只要有一只猫开着，新猫就带上这项能力（2026-11-26 在隔离运行时上实测两种情况）。适配层不依赖这条规则：只要注册表里有这条登记，每条建猫的路径（`POST /bots`、`/bots/:name/fork`、`/bots/import`）都**先把新猫的 id 写进屏蔽名单并确认，再去创建**。三条路径的 id 在创建前都已知（Bot 生成的随机 id，或由请求 key 推出），原生的屏蔽名单接受还不存在的 id（实测：这样建出来的猫一出生就是关的；删猫时原生会把它从名单里清掉）。所有猫都关着时也照样先屏蔽：一次到得晚的创建（请求在这边超时、引擎稍后才建好）如果正好落在某只猫被打开之后，原生就不再让它继承屏蔽了。这一段和开关走同一个进程内队列，开关请求不会插在「看登记」与「创建」之间；猫是不是已经存在，也是在队列里面现读的。

| 情况 | 结果 |
| --- | --- |
| 没有登记 | 不写，直接创建。创建的回答没等到（不是被明确拒绝）时把这个 id 记在内存里；之后第一次登记时，在一次全屏蔽之后、指向驱动之前把这些 id 也屏蔽并确认，确认不了就撤回登记 |
| 有登记，屏蔽写不进去或确认不了 | **不建猫**，503 `computer_unconfirmed` |
| 屏蔽已确认，创建的应答丢失，或创建之后 Bot 自己的步骤失败 | 猫可能已经建好，但已经先被屏蔽 |
| 同一个请求重放、猫早已存在 | 原样不动：使用者后来给它打开的不会被关掉 |
| 建好后再看一眼发现它仍开着（不该发生），而且关不掉 | 猫照样建好，回答里带 `notice` 如实说明（和「默认设置没写进去」的提示同一个字段，两句时以换行分开） |

**步骤。** `live` 事件里 `kind: "step"` 的步骤，用的是这条登记的工具时带 `area: "computer"`（工具名在 Claude Code 里是 `mcp__computer__…`，在 Codex 里是 `mcp:computer/…`）。界面据此显示「在用电脑」。登记的 id 是 `computer` 而不是驱动的名字，换驱动时界面和这里都不用改。

**没有做、以及要知道的边界。**

- Claude Code 的猫以 `bypassPermissions` 运行，不会每一步来问；驱动 0.34.0 的默认模式下也没有出现逐应用的询问。所以这个开关就是全部的许可：开着的猫可以操作这台电脑上任何应用。界面在打开时说明这一点。
- 猫看到的界面内容（窗口截图和界面结构）会作为工具结果发给它用的模型，并进入原生的对话记录。
- 「后台」不是保证：点按钮、填文字在后台完成；保存、菜单这类要求应用处于活动状态的操作，驱动会把窗口短暂提到前面；打开文件、启动应用也可能把别的窗口顶上来。后台发 ⌘S 不生效。
- 同一时间只有一只猫开着（上文）。这是开关上的规则，不是使用时的仲裁：做不到「几只猫各用各的应用、互不打扰」，也做不到按应用排队；那需要上游在调用路径上协调（已登记为上游需求）。另一只猫的回复会因为换猫而中断。
- 没有预览画面、没有显示正在用哪个应用、没有按应用限定范围、没有 Windows／Linux、没有应用内安装。
- 关闭不是原子的：从写屏蔽到那一轮真正结束（实测约 1 秒）之间，已经发出的那一个动作仍可能落地；已经送到桌面的输入撤不回。原生的队列不再列出调用，比 provider 进程真正退出早不到一秒，适配层以前者为准。
- 登记里记的是驱动的路径，引擎和 Agent 在调用时直接执行它，不经过本应用；本应用只在登记前和读状态时核对签名。
- 创建失败或 Bot 进程恰好在「屏蔽已写」与「创建」之间退出，名单里会留下一个不存在的 id（无害，不清理：清理可能把一只其实已经建好的猫放开）。没有登记时记下的「回答没等到的 id」只在内存里，Bot 重启即丢。模板创建的猫 id 由本仓库的 0005 补丁按请求 key 算出，有测试把两边的算法对在一起。
- 登记为上游需求：敏感能力默认关闭或允许名单（现在只有屏蔽名单）；撤销一轮执行已经拿到的工具（现在只能取消整轮）；把猫的身份传给 MCP 子进程（Claude Code 一侧有 `CAT_CAFE_CAT_ID`，Codex 一侧没有）；桌面操作的审批接入 Approval Hub。
